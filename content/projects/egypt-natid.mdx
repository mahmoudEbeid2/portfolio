## Problem

Almost every Egyptian product that onboards users — fintech, e-commerce, healthcare — asks for a 14-digit National ID. Most forms check it with a regex, which happily accepts IDs with impossible birth dates, unknown governorate codes or a wrong check digit. Teams then re-implement the same parsing logic (birth date, age, gender, governorate) in every project, often slightly differently.

## Solution

`egypt-natid` is a small, dependency-light TypeScript library that treats the ID as structured data instead of a string:

- **`validate(id)`** — strict structural validation: exactly 14 digits, century digit `2` or `3`, a birth date that actually exists and isn't in the future, a known governorate code, and a matching check digit.
- **`parse(id)`** — returns a typed `NationalIdAnalysis`: birth date, age, gender, governorate (English and Arabic names), economic region, `insideEgypt` and `isAdult`.
- **`sanitize(id)`** — converts Arabic-Indic digits (`٠١٢…`) to Latin digits and strips everything else, so pasted IDs don't fail for formatting reasons.
- **`generateId(options)`** — produces mathematically valid IDs for tests, with optional birth date, governorate and gender.
- **`filter()` and `stats()`** — run over arrays of IDs or objects (with a `key` option), filter by age, gender, region or governorate, and build demographic summaries. Invalid IDs are skipped instead of crashing the whole batch.
- **`egyid` CLI** — `validate`, `analyze`, `generate`, `filter` and `stats` straight from the terminal via `npx egyid`.

The last digit is a weighted checksum, which is what catches typos a regex can't:

```ts
// src/core/validate.ts (excerpt)
const checkDigit = Number(idStr[13]);
const multipliers = [2, 7, 6, 5, 4, 3, 2, 7, 6, 5, 4, 3, 2];
let sum = 0;
for (let i = 0; i < 13; i++) {
  sum += Number(idStr[i]) * multipliers[i];
}

const remainder = sum % 11;
const expectedCheckDigit = Math.abs(11 - remainder) % 10;

if (checkDigit !== expectedCheckDigit) {
  return false;
}
```

## Architecture

The source is split by responsibility:

- **`core/`** — pure functions: `validate`, `parse`, `sanitize`, `generate`, plus small extractors for birth date, gender, governorate and age.
- **`data/`** — a typed map of the 27 governorate codes (including `88` for IDs issued abroad), each with its English and Arabic name and economic region.
- **`domain/`** — the public types: `NationalIdAnalysis`, `NationalIdFilter`, `Gender`, `Governorate` and `EconomicRegion`.
- **`engine/`** — batch operations (`filter`, `mapWithAnalysis`, `stats`) built on top of `parse`.
- **`utils/`** — readable predicates such as `isMale`, `isAdult`, `isInsideEgypt` and `isFromGovernorate`.
- **`cli/`** — the `egyid` command, built with Commander, with one file per command.

The package is bundled with tsup into both CommonJS and ES modules with type declarations, exposed through a typed `exports` map, and also ships `NationalIdRegex` / `NationalIdSchemaMap` for plugging into form-validation schemas.

## Challenges

- **Real dates, not plausible ones.** Checking that the month is 1–12 and the day 1–31 still accepts dates like 31 February. The validator builds a real `Date` and confirms the year, month and day survive the round trip, then rejects dates in the future.
- **Messy input.** IDs come from forms, spreadsheets and Arabic keyboards — as strings, as numbers, with spaces or Arabic-Indic digits. The public functions accept `string | number`, and `sanitize` normalizes the rest.
- **Batch processing that doesn't explode.** `filter` and `stats` accept raw IDs, objects with an ID field, or already-parsed results, and silently skip invalid entries so one bad row doesn't break a whole report.
- **Test data that is actually valid.** `generateId` computes the same checksum as the validator and picks the serial digit to match the requested gender (odd for male, even for female), so generated IDs always pass `validate`.
