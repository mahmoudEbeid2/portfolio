## Problem

Moving money between wallets looks simple — subtract here, add there — until two requests hit the same wallet at the same time. Without protection, two concurrent transfers can both read the same balance, both pass the "enough funds?" check and both succeed: a classic double-spend. A wallet engine also has to keep a trustworthy ledger, hold suspicious high-value transfers for a human to review, and tell users about incoming payments without making every request wait on email delivery.

## Solution

PayNest is a wallet and ledger API built with NestJS, Prisma and PostgreSQL. Every transfer goes through the same guarded path:

1. **Validate** — positive amount, both wallets exist, no transfers to yourself.
2. **Lock** — take a Redis lock on the sender's wallet so only one transfer per wallet runs at a time.
3. **Screen** — transfers of `10,000` or more are not executed; they are stored as `PENDING` for an admin to approve.
4. **Move the money atomically** — re-read the balance, debit, credit and write the ledger row inside a single Prisma transaction.
5. **Side effects after commit** — invalidate cached balances, queue receipt emails in BullMQ and push a real-time `payment_received` event over Socket.io.

```ts
// src/transactions/transactions.service.ts (excerpt)
const lockKey = `wallet_lock:${senderWalletId}`;
const gotLock = await this.redis.acquireLock(lockKey, 5); // 5 seconds TTL

if (!gotLock) {
  throw new ConflictException('Another transaction is currently processing for this wallet. Please wait.');
}

try {
  // ...AML check for amounts >= 10,000...

  const transactionResult = await this.prisma.$transaction(async (tx) => {
    const currentSenderWallet = await tx.wallet.findUnique({
      where: { id: senderWalletId },
    });
    // ...
    if (Number(currentSenderWallet.balance) < amount) {
      throw new BadRequestException('Insufficient balance');
    }

    await tx.wallet.update({
      where: { id: senderWalletId },
      data: { balance: { decrement: amount } },
    });
    await tx.wallet.update({
      where: { id: receiverWalletId },
      data: { balance: { increment: amount } },
    });

    return tx.transaction.create({ /* ...TRANSFER, SUCCESS... */ });
  });
  // ...cache invalidation, BullMQ receipts, Socket.io notification...
} finally {
  await this.redis.releaseLock(lockKey);
}
```

The lock itself is a single atomic Redis command — `SET key LOCKED EX 5 NX` — so acquiring it and setting its expiry can't be split by another request.

## Architecture

- **API layer** — NestJS modules for `auth`, `users`, `wallets`, `transactions`, `admin` and `notifications`, documented with Swagger. A global `ThrottlerGuard` limits clients to 100 requests per minute.
- **Auth** — JWT with Passport, plus a `RolesGuard` and `@Roles()` decorator that separate `USER` and `ADMIN` endpoints.
- **Data** — PostgreSQL through Prisma. Three models: `User`, `Wallet` (balance stored as `Decimal(10, 2)`) and `Transaction`, an append-only ledger with `DEPOSIT` / `WITHDRAW` / `TRANSFER` types and `PENDING` / `SUCCESS` / `FAILED` statuses.
- **Redis** — two jobs: wallet locks (`wallet_lock:<walletId>`) and a balance cache (`wallet:<userId>`, 5-minute TTL) that is deleted whenever a balance changes.
- **Background jobs** — BullMQ `email-queue` with 3 attempts and exponential backoff; a worker sends HTML receipts over SMTP with Nodemailer.
- **Real time** — a Socket.io gateway pushes `payment_received` events to the receiver.
- **Reporting** — PDFKit generates a downloadable transaction statement per wallet.
- **Admin review** — admins list `PENDING` transactions and approve them. Approval takes the same wallet lock and re-checks the balance inside its own Prisma transaction before releasing the funds.
- **Infrastructure** — `docker-compose` runs the API, PostgreSQL 15 and Redis 7 together.

## Challenges

- **Double-spending under concurrency.** Wrapping the transfer in a database transaction alone wasn't the whole answer — two transactions can still read the same starting balance. The fix was layering a per-wallet Redis lock in front of the transaction, re-reading the balance *inside* the transaction, and releasing the lock in a `finally` block so a failed transfer never leaves a wallet stuck. A 5-second TTL guarantees the lock disappears even if the process crashes mid-transfer.
- **Keeping the cache honest.** Cached balances make reads cheap, but a stale balance in a wallet app is a bug. Every write path — transfers, deposits, approvals — deletes the affected `wallet:<userId>` keys right after the change commits.
- **Slow side effects.** Sending emails inside the request would make transfers slow and fragile. Receipts are queued in BullMQ instead, so the API responds as soon as the money has moved, and failed sends are retried automatically.
- **Human-in-the-loop for risky transfers.** High-value transfers become `PENDING` ledger entries instead of moving money, and the admin approval path reuses the same locking and balance checks as a normal transfer.

## Results

- Unit tests cover the critical paths, including rejecting a transfer when the wallet lock is already held and releasing the lock when the balance is insufficient.
- The whole stack starts locally with one `docker compose up`, and every endpoint is explorable through Swagger.
